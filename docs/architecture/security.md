# Security and Privacy

## Authentication and authorization
- **Users**: Microsoft Entra ID through MSAL.js nested app authentication (NAA), as proposed in [ADR-0002](../decisions/0002-auth-nested-app-auth.md). App registration type SPA, with redirect `brk-multihub://<add-in-origin>` (origin only, no path). Registered redirects: `brk-multihub://localhost:3000` (dev) and `brk-multihub://dimscale.github.io` (production, F-011). Check `Office.context.requirements.isSetSupported("NestedAppAuth", "1.1")` and show a clear "unsupported client" state when it returns false.
- **Graph, delegated (pane)**: delegated scopes only, requested incrementally per feature. The only one planned is `Mail.ReadBasic` (F-013 candidate list: `from` of recent Inbox messages, no body). The Graph token stays in the pane and is never sent to the backend. Admin consent is needed because Assignment required is on.
- **Graph, app-only (one exception, [ADR-0005](../decisions/0005-server-side-mail-processing.md), [F-013](../specs/F-013-automatic-reply-drafts.md))**: a second app registration "DIMSCALE Mail AI Drafts" reads incoming mail and creates reply drafts with Outlook closed. It has **no Entra Graph application consent**. Access is granted only by Exchange **RBAC for Applications** roles `Application Mail.Read` and `Application Mail.ReadWrite`, scoped to one mail-enabled group (direct members only; changes take 30 min to 2 h to apply). The roles don't include send. `Mail.Send` is never requested or assigned, and the code never calls send, reply, forward, move, copy or delete. Source: https://learn.microsoft.com/exchange/permissions-exo/application-rbac
- **Mail from other senders**: the backend reads only `from` of each new message first. Content is read and sent to OpenAI only when the sender is on that user's contact allow-list.
- **AI backend** ([F-002](../specs/F-002-authenticated-backend.md)): without token validation the backend would be an open, paid OpenAI proxy, so every request is authenticated by the function itself.
  - **Flow**: task pane → MSAL.js NAA → Entra access token for `api://<client-id>/access_as_user` (scopes `access_as_user` and `profile`, no Graph scope) → `Authorization: Bearer` on a `fetch` to the Supabase Edge Function. One single-tenant app registration is both SPA client and API, with `requestedAccessTokenVersion` = 2.
  - **Validation (in the function, before any other logic)**: signature against the tenant's v2.0 JWKS (selected by `kid`, remote key set with cache and refetch on unknown `kid`); `alg` RS256 only; `iss` exactly `https://login.microsoftonline.com/<tenant-id>/v2.0`; `ver` = `2.0`; `aud` = the client ID; `azp` = the client ID; `scp` contains `access_as_user`; `exp`/`nbf` with 60 s clock tolerance. Anything else gets 401.
  - **`verify_jwt = false`** for the function (`supabase/config.toml`): Supabase's platform check is for Supabase-issued JWTs and keys, not Entra tokens. With it off anyone can invoke the function, so the handler's own validation is the only gate.
  - **CORS**: exact allow-list from `ALLOWED_ORIGINS`, never `*`. Production value: `https://localhost:3000,https://dimscale.github.io` (localhost for dev, the Pages origin for production, origin only, no path). `Vary: Origin`, allowed header `authorization`, methods `GET, OPTIONS`. Non-allowed origins get no `Access-Control-Allow-Origin`.
  - **Responses and logs**: success returns only `{"ok":true,"name":<name or null>}`. Failure returns a generic 401 that does not say which check failed. Logs hold request id, status, a fixed reason code (for example `aud_mismatch`) and duration, never tokens, claims or the name.
  - **Who can sign in (F-002/AC-21)**: access is limited to one DIMSCALE Entra group through the enterprise app's **Assignment required = Yes** with only that group assigned (needs Entra ID P1 or P2). Users outside it get no token. This is enforced by Entra, not by function code. Source: https://learn.microsoft.com/entra/identity/enterprise-apps/assign-user-or-group-access-portal
  - **Data**: F-002 itself sends no email content (F-003 does, on click, see Third-party processing). Supabase receives only the access token, which carries user identifiers (`oid`, `tid`, `name`, `preferred_username`), so it is a processor of identity data (confirm project region for GDPR, decision D5).
- **Tokens**: MSAL manages its own cache. Our code never logs tokens, never sends Graph tokens to the backend, and never stores tokens itself.

## Secrets
- The OpenAI API key lives only in the backend secret store (for example Supabase function secrets).
- Nothing secret goes in the frontend bundle, the manifest, browser storage or git. `.env*` files are git-ignored. A code reviewer runs a secret scan on every review.
- **Not secret (F-002)**: Entra client ID, tenant ID, API scope, function URL, Supabase project ref and `ALLOWED_ORIGINS`. They may be committed or set with `supabase secrets set` (Supabase's env mechanism), and are configured per environment. The Supabase publishable key is browser-safe and not used.
- **Secret**: the Supabase CLI access token (developer machine only), the database password and secret keys (used only by the F-013 functions), the OpenAI key (`OPENAI_API_KEY`, configured in Supabase secrets on 2026-10-23), and for F-013 the **certificate private key** of the Drafts app (`GRAPH_CERT_PRIVATE_KEY`, only the public `.cer` goes to the admin), the webhook `GRAPH_CLIENT_STATE` (64 random characters) and `CRON_SHARED_SECRET` (also in Supabase Vault for the cron job). The SPA app registration has no client secret or certificate. `supabase/functions/.env` is git-ignored. Certificate expiry stops drafting (rotation reminder in the F-013 plan).
- **Public functions (F-013)**: `graph-webhook` (`verify_jwt = false`) is authenticated by comparing each notification's `clientState` in constant time and by a known `subscriptionId`; it also answers Graph's `validationToken` handshake. `auto-draft-cron` (`verify_jwt = false`) requires the `x-cron-secret` header (constant-time compare). `auto-reply-settings` uses the F-002 token validation plus a GUID `oid` and the configured `tid`, and keys every row by the token's `oid`. `analyze-message` (F-003, `verify_jwt = false`) uses the same validation (GUID `oid`, configured `tid`), CORS limited to `POST, OPTIONS`, and runs its checks in a fixed fail-closed order (config, method, token, body, kill switch, OpenAI config, cap, OpenAI, output validation). Sources: https://learn.microsoft.com/graph/change-notifications-delivery-webhooks, https://supabase.com/docs/guides/functions/secrets

## Email content handling
- **Untrusted input**: email subject and body are data. The backend places them in a clearly delimited user message, and the system prompt states that the content must not be followed as instructions.
- **No actions from model output**: the model returns structured JSON (validated against a schema). The UI shows it and only the user can act on it. The model has no tools.
- **Rendering**: AI and email text is rendered as React text nodes. `dangerouslySetInnerHTML` and `innerHTML` are forbidden for this content. Reply HTML passed to `displayReplyFormAsync` is built from escaped text.
- **Automatic drafts**: the output is validated against a strict schema and put in the draft body as escaped plain text with a marker line "[DIMSCALE AI draft - review and edit before sending]" and the category "DIMSCALE AI draft". The user reviews and sends every draft.
- **Minimization**: send only what the feature needs: plain-text body (not HTML), subject, sender display name and domain, truncated to the limit in each spec. No attachments, no recipient lists unless a spec justifies it.
- **Logging**: no email content, addresses or tokens in browser console logs, backend logs or error reports. Log request ids, durations and status codes only.

## Third-party processing (OpenAI)
- Email content leaves Microsoft 365 when it is sent to the OpenAI API. Confirm with DIMSCALE that this is acceptable under its GDPR obligations (decision D5: a DPA with OpenAI, transfer safeguards, the region).
- **OpenAI terms (checked 2026-10-23)**: API data isn't used for training by default; abuse-monitoring logs are kept up to 30 days; `/v1/responses` stores application state for 30 days when `store` is true (the default), so every call sends `store: false`; EU data residency (`eu.api.openai.com`) needs Zero Data Retention, Modified Abuse Monitoring or a similar control approved by OpenAI. Sources: https://developers.openai.com/api/docs/guides/your-data, https://developers.openai.com/api/docs/guides/migrate-to-responses
- **Automatic drafts (F-013)** send OpenAI, without a per-message user action, only: subject (255 chars), the sender's display name and **domain** (never the address), and the unique body text (4,000 chars), and only for senders the user chose. No recipients, headers, IDs, attachments or quoted thread.
- **User-initiated analysis (F-003)**: flow **pane → `analyze-message` → OpenAI**, only when the user clicks "Resumir" or "Sugerir resposta" (never on load, item change or tab switch). The pane sends, and the function forwards, exactly: subject (≤ 200 chars), the sender's display name (≤ 100), the sender's **domain only** (never the address), and the plain-text body (≤ 4,000 chars) **including any quoted earlier messages**, which are third parties' personal data. No recipients, full address, item ID, dates, attachments or user identity. The OpenAI request has `store: false`, no `tools`, strict JSON schema, model `gpt-6-luna` (set by `OPENAI_MODEL`), `reasoning.effort` low, `max_output_tokens` 2,000. The call goes through the same F-002 token validation (GUID `oid`, configured `tid`); no Graph call, no manifest change (`ReadItem` only).
  - **Cost control**: a per-user (50) and global (1,500) cap per UTC day, taken in Postgres before every OpenAI call (`ANALYZE_DAILY_CAP_PER_USER`, `ANALYZE_DAILY_CAP_GLOBAL`; invalid or above 1,000,000 → default), and a kill switch `ANALYZE_DISABLED=true` (503, read per request, no redeploy). Requests over 16 KiB are rejected early.
  - **Output**: validated again in code; summary and reply contain **no link or email address at all** (even ones in the email) and no `<`/`>` (rejected, not sanitised). Rendered as text nodes; the reply passed to `displayReplyFormAsync` is HTML-escaped. The user reviews and sends.
  - **Status (D5)**: the model is chosen (`gpt-6-luna`); the DPO's answer is pending, so **only test emails are used** until D5 is answered. The pane shows a privacy notice before any click.
  - **Amendment 2026-10-29 (Kutools-style pane, [F-003](../specs/F-003-analyze-summary-and-reply.md), [F-012](../specs/F-012-taskpane-design.md))**, three actions on the same function, caps, kill switch and validation:
    - **`summarize` by click, by the ribbon "Resumo" button** (one request when the pane opens from `resumo.html`; the button's tooltip says the text goes to OpenAI), **or by auto mode**.
    - **Auto mode (new trigger):** only when the user has switched "Resumo automático" on (off by default; a dialog states the exact data sent before it turns on; a visible "ligado" line while on; off at any time). While on, **every email the user opens while the pane shows the Resumo tab** is sent to OpenAI with the summary fields above, after an 800 ms debounce, one request per email per pane session; in-flight requests for a previous email are aborted (the slot may already be used and billed). It pauses for the pane session on the daily cap, 401, `disabled` or `ai_not_configured`, and never retries by itself. It never runs for reply or translate. A pane flag `AUTO_SUMMARY_AVAILABLE` hides it entirely; proposed `false` in production **until D5 is answered**, because auto mode sends real mail as the user reads it, which "test emails only" cannot cover. This is a separate DPO point (D5 question 5).
    - **`translate`:** subject (≤ 200) and body (≤ 4,000) only; the function rejects a non-empty sender name or domain for this action. Output: translated subject and body, plain text, no link, address or `<`/`>` (rejected), `max_output_tokens` 4,000.
    - **`reply` refinement (F-003 amendment d, 2026-10-29):** after a suggestion the user can type a change request ("Pedir alterações"). The request adds two fields to `reply`: `instruction` (typed by the user, trimmed, ≤ 300 chars) and `draft` (the current suggestion, ≤ 2,000 chars; AI output sent back, so untrusted like the email). Both or neither. They go in labelled sections after the email with the sentence that the email and the draft are data and the instruction may change only the draft text. This is the first client free text in a prompt. Output checks are unchanged and run against the email text only (plain text, `<`/`>` rejected, no link, no address), so neither field can introduce a link or an address. The server keeps no history. Neither field is logged. Each revision counts against the daily caps. No action is triggered: the user still opens the reply form and sends.
    - **Reply options:** `language` and `tone` are enums mapped by the function to fixed instruction sentences; no user free text reaches the instructions (the optional refinement `instruction` and `draft` below travel in the input, in their own delimited blocks), and the options never enter the delimited email block. Defaults produce the same request as before.
    - **Preference storage:** one boolean `autoSummary` in `Office.context.roamingSettings`, i.e. in the user's own Exchange mailbox, per user and per add-in (Microsoft: "shouldn't be considered secure storage"; fine for a non-sensitive flag). Not in Supabase, not in browser storage. `localStorage` was rejected because `dimscale.github.io` is shared with every Pages site of the org (ADR-0004), so another site could set the flag and switch auto mode on without consent. Sources: https://learn.microsoft.com/javascript/api/outlook/office.roamingsettings, https://learn.microsoft.com/office/dev/add-ins/testing/runtimes
    - **Manifest:** two ribbon buttons "IA" and "Resumo" (F-012 AC-48), still `ReadItem` only, no new scope. A manifest change means a `<Version>` bump and an admin (re-)upload; the final manifest goes to the admin only after the live ribbon check (F-012 AC-52/AC-53).
- Show users a one-line notice in the panel that content is processed by an external AI service (the Automático tab, formerly Responder, and the Resumo, Resposta and Traduzir tabs say so; auto mode adds its own dialog and "ligado" line).

## Stored data (Supabase, F-013)
The backend is no longer stateless. Postgres (eu-west-1) has RLS enabled with no policies and is reached only by the functions with the secret key; the client never writes it.
- **Stored**: per user the Entra `oid`, a SHA-256 of the user's own address, the enabled flag and status; the user's chosen contact addresses (plain text); Graph subscription IDs and expiry; a queue of message IDs (immutable ID) with status and a fixed reason code.
- **Not stored**: subject, body, display names, AI output, tokens.
- **F-003 usage counter** (`analyze_usage`, same RLS lock, service role only): a pseudonymised user key (**unsalted SHA-256** of the lower-cased `oid`, so it is pseudonymised, not anonymous), the UTC day and a count. Nothing else, no content or AI output. Rows older than 2 days are purged **inside the `an_take` function**, so the purge runs only when someone uses the feature and rows can outlive 2 days otherwise (accepted: tiny, pseudonymised). Whether this is acceptable is part of D5 (DPO).
- **Contact allow-list = personal data of third parties.** Retention: until the user removes it or presses "Apagar tudo"; a user disabled for 90 days or `not_in_scope` for 30 days is deleted with the contacts (proposal); an operator script deletes by `oid` for leavers; queue rows are deleted after 30 days. Deleted rows may stay in Supabase backups (not verified). Lawful basis, retention and the privacy notice are DPO decision D15 (D-3).
- **Logs** (`analyze-message` logs only `fn`, `id`, `method`, `status`, `reason`, `ms`): request ID, function, internal `user_id` (not the OID), status, fixed reason code, attempt, duration. Never message IDs, subjects, bodies, addresses, headers, AI output, tokens, `clientState` or the certificate assertion.
- **Residual risks (accepted only by the user)**: a forged `From` of a listed contact can trigger an unsent draft and an OpenAI call; a prompt-injection email can produce an unwanted draft text (marker line and category, fixed instructions, no tools, plain text, never sent by the system).

## Hosting (GitHub Pages, [ADR-0004](../decisions/0004-taskpane-hosting.md), [F-011](../specs/F-011-github-pages-hosting.md))
- **Data flow**: push to `main` → GitHub Actions (typecheck, lint, tests, production build, manifest validation) → GitHub Pages → Outlook loads the task pane from `https://dimscale.github.io/DIMSCALE-EMAIL-AI/`. The page then calls Entra (MSAL NAA) and the Supabase function as described above. Pages serves static files only and sees no email content.
- **Public artifacts**: everything under the Pages URL is public, including the production `manifest.xml`. It holds only non-secret identifiers (add-in Id, URLs, `ReadItem`). Authorization is the Entra token validated by the function, not hiding the page.
- **No production source maps** are published. Dev builds keep them.
- **Shared origin risk (accepted, ADR-0004)**: `dimscale.github.io` is one browser origin for every Pages site in the `dimscale` org. They share `localStorage`/`sessionStorage` (including the MSAL cache) and are all covered by the Entra redirect and `ALLOWED_ORIGINS` entries. Mitigation: only org members can publish Pages, a token still needs the user's Entra sign-in, and the rule **no other Pages site under the `dimscale` org origin without review**. Moving to a custom domain (ADR-0004 option B) would remove the sharing.
- **CI supply chain (deploy workflow)**: every action pinned to a full commit SHA (version in a comment); top-level `permissions: contents: read`, and only the deploy job adds `pages: write` and `id-token: write`; the deploy job runs only on `main` (never on pull requests) and needs the check job; no `pull_request_target`; no repository secrets (the Pages actions use the automatic `GITHUB_TOKEN`); `npm ci --ignore-scripts`. SHA pins get no automatic Dependabot alerts, so review them when touching the workflow.

## Supply chain
- Dev-only tooling (`office-addin-debugging`, `office-addin-dev-certs`, and others) pulls packages with install scripts: `keytar`, `@azure/msal-node-extensions`, `@microsoft/m365agentstoolkit-cli`, `core-js`. None of them ship in the bundle. CI uses `npm ci --ignore-scripts` (see Hosting).

## Classification safety
- The "potentially suspicious" label is advisory, shown with its reasons and a "may be wrong" notice. The add-in never reports phishing, moves mail to junk or blocks senders on its own.
